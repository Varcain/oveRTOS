# Versioning

oveRTOS has one version number, `MAJOR.MINOR.PATCH`, defined in
`include/ove/version.h`. That header is the source of truth. The packages built
from the tree state the same number, and `make lint` checks that they agree:

| Package | Manifest |
|---|---|
| C headers | `include/ove/version.h` (`OVE_VERSION_MAJOR`, `_MINOR`, `_PATCH`, `OVE_VERSION_STRING`) |
| `ove` CLI | `config/ove-cli/pyproject.toml` |
| Rust crates `ove`, `ove-macros`, `ove-allocator` | their `Cargo.toml`; `ove`'s requirement on `ove-macros` must admit the version |
| Zig module | `bindings/zig/ove/build.zig.zon` |

## Reading it

| Language | Numbers | Packed (for comparisons) | String |
|---|---|---|---|
| C | `OVE_VERSION_MAJOR` / `_MINOR` / `_PATCH` | `OVE_VERSION`, `OVE_VERSION_NUMBER(maj, min, patch)` | `OVE_VERSION_STRING` |
| C++ | `ove::version::major` / `minor` / `patch` | `ove::version::packed`, `ove::version::number()` | `ove::version::string` |
| Rust | `ove::version::MAJOR` / `MINOR` / `PATCH` | `ove::version::VERSION`, `ove::version::number()` | `ove::version::VERSION_STR` |
| Zig | `ove.version.major` / `minor` / `patch` | `ove.version.packed_version`, `ove.version.number()`; `ove.version.semantic` | `ove.version.string` |

The packed form is `(MAJOR << 16) | (MINOR << 8) | PATCH`, so MINOR and PATCH
stay within 0..255. In C it works in the preprocessor:

<!-- ove:fragment -->
```c
#if OVE_VERSION >= OVE_VERSION_NUMBER(0, 2, 0)
/* something 0.2.0 added */
#endif
```

All of these are compile-time constants; there is no run-time query. The
substrate is always built from source together with the application, so the
headers and the code they describe cannot differ.

The HTTP server's `/api/info` route reports the version as `"version"`.

## Version versus build identity

The version names a release. Which sources a particular firmware image came from
is a separate question, answered by `ove/build.h`: `OVE_BUILD_OVERTOS_REV` (the
oveRTOS git revision), `OVE_BUILD_LXP_REV` and `OVE_BUILD_ID`, generated by
`ove build`. Two images of the same version can differ in those.

## Bumping it

The numbers follow [semantic versioning](https://semver.org/): MAJOR for
incompatible API or ABI changes, MINOR for compatible additions, PATCH for
fixes. While MAJOR is 0, a MINOR bump may also break compatibility.

To bump:

1. Change the three numbers and `OVE_VERSION_STRING` in `include/ove/version.h`.
2. Change the version in each manifest in the table above. When MAJOR or MINOR
   changes, also change `ove`'s requirement on `ove-macros` in
   `bindings/rust/ove/Cargo.toml` (`"MAJOR.MINOR"`).
3. Change the `OVE_VERSION*` constants in `bindings/rust/ove/src/bindings_stub.rs`,
   the stand-in for bindgen's output that docs.rs builds use.
4. Refresh the tracked `Cargo.lock` files that pin the crates
   (`bindings/rust/ove`, `bindings/rust/ove-macros`, `tests/rust`,
   `tests/benchmarks/rust` and the `apps/rust/*/*` examples), for instance with
   `cargo metadata --offline --format-version 1 >/dev/null` in each, which
   re-reads the path dependencies' versions without updating anything else.
   The lint's clippy pass builds with `--locked` and fails on a stale lock.
5. Run `make lint`. Its `version-pin` check names any manifest, or the stub,
   that still disagrees, and the Rust crate fails to compile when its
   `Cargo.toml` and the header differ.

The `ove` CLI reinstalls itself into `.venv` on the next `make` once
`pyproject.toml` changes.
